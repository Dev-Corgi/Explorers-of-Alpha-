# mega_evolve — 페이즈 3

메가진화·이로치 메가진화의 모든 새 기능은 이 모듈에서 구현한다.
기존 `base_stats_speed`, `spinda_ev_speed`, `balance_change`, `bug_fixes`,
`luminous_evolution`, `z_move_v2`는 입력 기능이며 해당 모듈 자체를 수정하지 않는다.
관련 호출·할당은 `patch_engine`에서 연결한다.
카트리지 용량 정책은 [ROM_CAPACITY.md](ROM_CAPACITY.md)에 기록한다.
필요할 때 128MiB에서 256MiB로 확장하며 RAM/ID 저장 폭과 별도로 처리한다.

현재 `manifest.yaml`의 `phase: 3`, version 5는 기존 최종형 546개 MD 행의
특성 1·2 배정과 실제 배정된 206개 특성의 일반 효과를 연결한다.
필요한 이름·설명 1174개 영어/한국어 문자열도 함께 적용한다.
기반 범위는 [PHASE2.md](PHASE2.md), [PHASE1.md](PHASE1.md)에 기록한다.
페이즈 0의 정규화 자료와 원본 개체 대응은 그대로 유지한다.
새 메가·이로치 형태와 강화 개별 효과는 다음 페이즈에서 적용한다.
`FULL_STACK_MODULES`에서 `luminous_evolution` 뒤에 등록했고 한글은 이후에 적용한다.
검증하지 않은 다음 단계 번호는 엔진에서 거부한다.

## 자료와 재현

페이즈 3 구현은 별도 비압축 실행 파일을 heap RAM으로 로드한다.
기존 ov36 빈 공간에는 8KiB 호출 bootstrap만 두며 특성 ID 배정표는 16비트를 유지한다.
최초/반복 호출, 재배치, CPU 캐시 처리, 던전 종료 후 해제·재로딩은
`python -B -X utf8 -m true_patches.mega_evolve.verify_loader`로 ARM 검증한다.
파일 IO와 메모리 할당은 이 검증에서 모델링되며 실제 최대 부하 RAM 검증은 남아 있다.
일반 효과별 ARM 검증과 기존 효과의 소비자 출처는 PHASE3_WORK.md,
NATIVE_REUSE.md, data/phase3_coverage.json에 구분해 기록한다.

`data/registry.json`은 사용자 CSV 두 개와 종족값 XLSX, 기준 Alpha 롬,
로컬 공식 폼 데이터에서 생성한다. 원본 자료·SpriteCollab·기존 출력 에셋은
읽기만 한다. 원본 파일 SHA-256과 행 위치를 기록한다. 외부 원본은 Git에 복사하지 않는다.

```powershell
.venv\Scripts\python.exe -B -X utf8 true_patches\mega_evolve\phase0.py --refresh
.venv\Scripts\python.exe -B -X utf8 true_patches\mega_evolve\verify.py
.venv\Scripts\python.exe -B -X utf8 true_patches\mega_evolve\verify_phase1.py
.venv\Scripts\python.exe -B -X utf8 true_patches\mega_evolve\verify_phase2.py
.venv\Scripts\python.exe -B -X utf8 -m true_patches.mega_evolve.verify_phase3_suite
```

`--refresh`는 이 모듈의 JSON만 갱신한다. 옵션 없이 실행하면 재생성 결과와
저장된 JSON을 비교한다. 검증은 롬 빌드·NDS 출력·state 파일 출력을 하지 않는다.
페이즈 0 검증은 무변경 자료 검증 경로를 호출한다. 페이즈 1 검증은 기존
영문 풀스택을 메모리에 읽어 적용·ARM 실행하고 입력 파일 해시를 비교한다.

## 페이즈 0 결과

- 특성 배정 322행, 종족값 308행, 공통 원본 ROM ID 320개.
- 쉼표로 묶인 ID와 메가 분기를 펼친 논리 대상은 326개다.
  이는 새 포켓몬 326종이나 최종 물리 ID 수를 의미하지 않는다.
- 교체·별칭 반영 후 배정 특성은 206개. 모두 일반·강화 구현 대상이다.
- 특성 효과표의 번호는 본가 번호다. ROM 특성 ID로 그대로 쓰지 않는다.
  기존 Alpha 이름·한글 번역으로 확인 가능한 ROM ID 후보도 별도 기록한다.
  후보가 없는 특성은 새 특성이라고 단정하지 않고 페이즈 2에서 이름·효과
  대응과 확장 ID를 확인한다.
- 원시회귀·오리진폼은 공식 메가 단계. 동일 계열 원본의 메가 목표도
  해당 공식 폼으로 지정한다. 세 오리진의 종족값은 요청한
  HP/Atk/Def/SpA/SpD/Spe = 100/130/130/160/130/130으로 우선 적용한다.
- 일반·이로치 메가는 같은 타입·종족값을 공유한다.
- 원본 ID와 분기로 논리 키를 구성한다. 물리 ID는 페이즈 3에서 배정한다.
  기존 공식 형태, 성별 대응, 기존 저장 개체, 스토리 개체는 각각 구분한다.

## 확정 규칙

- 최종진화형 → 메가: 진화의 샘, 레벨 80 이상, 아이템 없음.
- 메가 → 이로치 메가: 추가 레벨·아이템 조건 없음. 같은 방문에서 연속 가능.
- 이로치 퇴화는 같은 분기의 메가로, 메가 퇴화는 원래 최종진화형으로.
- 메가 분기는 진화 시 선택. 이후 분기 변경 기능은 별도 규칙 전까지 제공하지 않는다.
- 일반형은 특성 1·2, 메가는 일반 1·2·3, 이로치는 강화 1·2·3을 동시에 처리한다.
- 같은 특성 중복 보유는 한 번 적용. 서로 다른 특성은 효과별 우선순위가 필요하다.
- 날카로운발톱 → 단단한발톱, 전지전능/Omnisense → Omniscience.
- 일렉트릭메이커 → 일렉트릭스킨, 서핑테일 → 쓱쓱.
  일렉트릭필드·강한 필드·부스트에너지는 이번 범위에 포함하지 않는다.
- 불굴의마음은 이동 배속이 아닌 스피드 저장단계 +1/+2.
- 고대활성은 도구 조건 없이 새 햇살/처치에서 최고 능력 저장단계 +1/+2.
  햇살은 새 적용당 한 번, 처치는 공격 행동당 한 번.
- 스피드 저장단계, 계산단계, 이동속도는 별개. 저장 중립 10, 범위 4..16.
- 쾌청/비의 해당 기술 위력 ×1.2. 큰가뭄/폭우는 기존 효과에 해당 위력 ×1.5.
- 모래바람은 바위·땅·강철 방어/특방 ×1.2, 강한 모래바람은 ×1.5.
- 싸라기눈은 설경으로 변경하고 정기 피해 제거. 얼음 방어/특방 ×1.2,
  강한 설경은 ×1.5. 보정은 계산에서 한 번만 적용하며 저장 수치를 바꾸지 않는다.
- 강한 날씨는 강한 모래바람·강한 설경·강풍을 포함한다.
  일반 날씨는 강한 날씨를 덮어쓰지 못하며 다른 강한 날씨로 변경 가능하다.
  최근 유효한 강한 날씨가 우선. 강도와 발생원·유지/해제 조건은 분리한다.
- 날씨 특성 트리거는 강도가 아니라 날씨 계열로 확인한다.
  복합 타입의 날씨 방어 보정은 중복하지 않고 ×1.5는 ×1.2를 대체한다.
- 변신/특성 교환/일시 타입 변경은 영구 형태와 분리하고 해제 시 복원한다.
- 없는 초상화는 기존 초상화를 재사용한다.

## Omniscience / 전지전능

기준 롬의 실제 이름은 **Omniscience**, ROM 특성 ID **250**이다.
이름 인덱스 18701, 설명 인덱스 18957. 일반 아르세우스 MD 537은
Multitype(116), 스토리용 MD 1137은 Omniscience(250)다.
두 개체는 자동 통합하지 않는다. 기존 설명은 유리한 공격 타입으로 변화 및
피해 증가, 방어 시 저항 타입으로 변화 및 피해 감소, 능력 저하·급소 면역이다.
정확한 기존 배율은 설명에 없으며 실제 ARM 경로 검증이 필요하다.

강화 효과는 기존 효과에 **심판의 Z-Move 처리**를 추가한다.

- 활성 전지전능Ⅱ 보유자가 심판(467)을 사용할 때만 적용.
- 행동 시작 시 현재 주 타입을 고정한다. 공격 중 기존 전지전능이 타입을
  바꾸거나 여러 대상을 공격해도 그 행동의 Z 타입은 다시 선택하지 않는다.
  복합 타입의 주 타입 사용은 현재 설계 기본값이다.
- 기존 Z-Move 기준 노말 위력 360, 나머지 180 및 해당 타입 추가 효과.
  기술 자체의 심판 PP 처리와 기존 전지전능 효과를 유지한다.
- 게이지 요구·소모·초기화 없음. 통상 공격/피격/처치의 기존 게이지 획득은 유지.
- 수동 Z-Move의 메뉴, 임시 4번 기술 슬롯, pending 플래그를 건드리지 않는다.
  별도 행동 컨텍스트로 기존 위력·타입 효과 경로를 재사용한다.
- 추가 효과의 행동당 발동 횟수는 기존 Z-Move를 따른다.
  특성 억제, 일반 전지전능, 심판 이외 기술에는 이 강화가 작동하지 않는다.

`z_move_v2`의 기존 효과 판정은 **pending 상태 + 기술 559**를 요구한다.
심판 467의 타입만 변경해서는 Z 위력·추가 효과가 발동하지 않는다.
따라서 페이즈 7에서 그 조건을 연결하는 mega_evolve 소유 훅이 필요하다.
앞선 수동 Z-Move의 상태를 저장/복원하고 사용자·기술·행동 범위를 확인하여
다른 팀원에게 효과가 새지 않게 한다. 기존 특성의 정확한 피해 배율은 그대로 둔다.

## 종 ID·능력치·저장 구조 결정

1. 기존 MD는 1155엔트리, 기존 종족값 표는 기본 600개 × 6개의 uint8.
   제공 종족값에는 **277**이 있으므로 새 표는 각 능력치를 uint16으로 저장한다.
   기존 CalcStat 소비자에 mega_evolve 조회 경로를 연결해야 한다.
2. 기존 기본형/성별/보스 분류는 단순 `ID+600`과 같지 않다. 조사 대상에서
   +600 엔트리 226개는 암컷 대응 후보, 75개는 대체/스토리 후보다.
   이는 자동 변환 허가가 아닌 분류 증거다. 1137은 대표적인 스토리 개체다.
3. **일반 저장의 종 ID는 11비트**다. 기준 ARM9의 0x02059358(쓰기),
   0x02059480(읽기)에서 record+4를 11비트로 직렬화하는 실제 명령을 확인했다.
   단순 신규 2단계+성별 복제의 상한 계산은 총 2269엔트리로 2048개 범위를 넘는다.
   이 수는 기존 형태 재사용을 하기 전의 용량 경고다.
4. 확장 방향은 명시적 MD/폼/성별 대응표와 버전 있는 저장 코덱이다.
   영구 단계는 해당 형태 ID로 식별하고, 원래 형태와 분기는 대응표로 복원한다.
   기존 2개의 진화 이력 바이트와 도핑 V를 새 플래그 저장소로 쓰지 않는다.
5. 기존 EVS1 저장 확장은 0xB700..0xC644를 사용한다. 겹치게 쓰지 않는다.
   555개 동료 슬롯 수는 종 수와 별개이며 종 추가 때문에 동료 슬롯을 늘리지 않는다.
   일반 저장, 모험팀/미로 복사, 던전 중간 저장, 변신 복원의 모든 경로를
   페이즈 4에서 실행 검증한 뒤 실제 포맷과 물리 ID를 확정한다.
6. 새 메가 형태는 최종진화 보정 ×1.0이며 기존 진화 그래프에 붙여
   기본형의 진화계열 배율을 바꾸지 않는다. 보스/스토리의 기존 능력 처리도 분리한다.
7. 기라티나의 일반 폼변경에서 오리진을 제거하여 레벨 80 진화 조건 우회를 막는다.
   Spring 2..4 폼 선택기와 기존 역진화 테이블도 새 분기에 맞는 별도 조회가 필요하다.
8. 일반 기라티나 행과 기존 오리진 행의 특성 배정이 다르다.
   최종형의 특성 1·2를 유지하는 신규 진화 경로와 기존 오리진 개체의
   프로필을 한 MD 엔트리에 무조건 합치지 않는다. 같은 외형을 공유하더라도
   원래 프로필을 유지하는 별도 ID/조회가 필요하다. 차이는 JSON에 기록한다.

## 에셋 조사 범위

JSON의 sprite 항목은 로컬 tracker와 실제 XML 존재 여부로 만든 후보 목록이다.
일반 공식 폼과 Normal/Shiny 아우라 후보를 구분하고 지역폼은 기본 아우라로
잘못 대응하지 않는다. 이미지나 압축을 푼 ROM 데이터를 Git에 넣지 않는다.
픽셀, XML 동작 누락, 프레임, 팔레트, WAN 변환은 페이즈 5에서 검증한다.

현재 normalized 아우라 도구는 Primal을 제외한다. 공식 원시 형태의 shiny
아우라는 원본 폴더까지 포함해 별도 확인해야 한다. 공식 폼 스프라이트가
없으면 일반 아우라를 사용할 수 있지만 공식 폼의 shiny 아우라가 없다고
임의의 다른 폼으로 대체하지 않는다. 누락은 페이즈 5 해결 항목으로 기록한다.

## 다음 단계와 검증 경계

페이즈 1 스피드/날씨 → 2 특성 엔진 → 3 일반 특성 정비 → 4 형태 데이터
→ 5 에셋 → 6 진화의 샘 → 7 강화 특성 → 8 통합 검증 순서다.
물리 ID·저장 코덱 검증은 페이즈 0의 확장 조사에 이어 실제 형태 데이터
페이즈에서 완료한다. JSON의 `phase4_requirements`는 형태 추가의 선행 조건이다.

페이즈 0 검증은 자료 일치, 분기/별칭, 공식 폼 우선 규칙, 출처 해시,
11비트 저장 명령, uint8 한계, 특성 범위, 엔진 무변경을 확인한다.
미구현 런타임 기능이나 게임 화면의 완료를 인증하지 않는다.
새 훅은 적용 시 동굴을 할당하고 team_push 예약 구간을 보존한다.
새 문자열은 빈 인덱스를 선택하고 LogMessageById에는 인덱스+1을 넘긴다.
한국어는 마지막 모듈에서 실제 설치된 영어와 일치할 때만 적용한다.

페이즈 3은 일반 특성 배정·이름/설명·효과를 공개 적용 경로에 연결한다.
변경/신규 효과의 실행 사례와 그대로 재사용하는 기존 효과의 코드 출처를
별도로 보관한다. 기존 효과를 전부 새 코드로 다시 작성하지 않는다.
테스트는 외부 UI·IO·할당·일부 native 서비스를 모델링하므로 전체 던전 전투,
최대 부하 RAM, 실제 기기 실행까지 인증하지 않는다. 이 통합 검증은 페이즈 8이다.
