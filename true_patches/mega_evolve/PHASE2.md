# mega_evolve 페이즈 2 — 특성 공통 엔진

`manifest.yaml`은 version 3, phase 2다. 기존 페이즈 1을 포함해 적용한다.
이 단계는 특성 엔진 기반이며 배정표를 monster.md에 적용한 단계는 아니다.

## 구현

- 배정된 206개 특성은 안정적인 16비트 ID 256..461을 사용한다.
  일반/강화는 별도 0/1 등급이다. 본가 효과표 번호나 강화 특성을 ROM의
  8비트 ID로 잘라 넣지 않는다. 179개는 기존 Alpha 효과 ID에 대응한다.
  나머지 27개도 유효한 복사/강화 대상으로 등록한다. 효과 구현 인증과는 별개다.
- 기존 1..254 ID는 호환 조회하고, 배정되지 않은 기존 특성도 유지한다.
  이름만 같은 기존 ID24/99, 125/251은 효과가 같다고 단정해 통합하지 않는다.
  일렉트릭스킨/쓱쓱 교체는 이전 번역 후보 Electric Surge/Surge Surfer로 매핑하지 않는다.
- 던전의 20개 개체 각각에 원래 프로필과 현재 임시 프로필을 세 슬롯으로 둔다.
  슬롯은 16비트 종류+강화 등급을 반환한다. 동일 특성 조회는 한 번 적용할 수
  있는 판정으로 합치고, 일반/강화가 동시에 있으면 강화 등급을 우선한다.
- 기존 AbilityIsActive 진입점을 연결한다. veneer, 방어자/다른 개체 판정,
  기존 개별 효과의 공통 조회도 세 번째 특성을 볼 수 있다.
  위액, 특성 억제 도구(기존 exclusive effect 39), 기존 인접 화학변화가스
  판정을 유지한다. 강화 화학변화가스의 방 범위 효과는 페이즈 7이다.
- 트레이스는 유효한 세 슬롯의 중복 종류를 제거하고 균등 선택한다.
  중복 종류의 등급은 높은 쪽을 고른다. 트레이스Ⅱ는 일반 후보를 강화한다.
  구현된 강화 효과만 복사하는 별도의 후보 필터는 없다.
- 실제 스킬스왑과 역할 경로는 세 슬롯과 등급 전체를 임시 교환/복사한다.
  기존 특성 복원 함수도 원래 프로필을 복구한다. 현재 특성 비교는 세 슬롯과
  등급을 포함한다. 원래 종 ID나 메가 단계는 쓰지 않는다.
- 기존 코드가 두 특성 바이트를 바꾸면 변경 슬롯을 임시 일반 특성으로 받아들인다.
  원래 프로필은 바뀌지 않는다. 같은 바이트 값으로 덮어써서 등급을 바꾸는
  개별 효과는 페이즈 3/7에서 직접 API를 호출해야 한다.
- 행동 컨텍스트 API는 최대 4단계 중첩과 컨텍스트당 64개 발동 기록을 지원한다.
  (보유자, 종류, 사건, 대상)으로 한 번만 허용한다. 대상 0은 행동 전체,
  실제 대상 주소는 대상별 판정이다. 연결기/다단히트/범위 효과의 실제 경계와
  각 효과의 사건 선택은 페이즈 3/7 디스패처에서 연결한다.
  잘못된 종료 순서나 초과 중첩/기록은 허용하지 않는다.
- 페이즈 1 스피드/날씨 조회도 확장 엔진을 사용한다. 단순Ⅱ의 스피드 감소는
  두 배가 되지 않고, 클리어바디Ⅱ는 자신의 스피드 감소도 차단한다.
  날씨 발생원은 16비트 특성과 발생 당시 등급을 기록하여 등급 변경 후
  예전 강화 날씨 발생원이 유지되지 않게 한다.

## API와 상태 경계

- `ME_SetAbilityProfile(entity, uint32[3], count)`: 원래 프로필 공급.
  값의 하위 16비트는 종류, bit16은 강화 등급. 전부 검증한 후 한 번에 적용한다.
  기존 ID로 입력하면 대응되는 정규 ID로 변환한다. 255와 미등록 ID는 거부한다.
- `ME_GetAbility(entity, slot, active_only)`, `ME_AbilityGrade`, `ME_AbilityActive`:
  세 슬롯/등급/억제 조회. UI에서 사용하는 조회 API도 이 경로다.
- `ME_CopyAbilities`, `ME_SwapAbilities`, `ME_RestoreAbilities`: 임시 변경/복원.
- `ME_BeginAction`, `ME_ClaimEffect`, `ME_EndAction`: 행동당 발동 제어.
- 개체/monster 포인터/원래 종이 달라지거나 층이 바뀌면 이전 은행을 폐기한다.
  새 층의 영구 프로필은 페이즈 4의 종/폼 데이터 공급자가 다시 설정한다.
- 스피드/날씨 1024바이트 컴포넌트 코덱은 schema 2이며 schema 1도 읽는다.
  날씨 발생원의 종류·등급을 저장한다. 특성 은행 전체 저장 및 실제 일반 저장/
  중간 저장 연결은 기존 계획대로 페이즈 4에서 수행한다.

## 직접 슬롯 접근 조사와 다음 단계

`data/phase2_slot_audit.json`은 기존 풀스택의 두 바이트 슬롯 접근 후보를 기록한다.
선형 디스어셈블 결과이므로 데이터의 오인식도 있을 수 있으며 후보를 전부
특성 접근이라고 인증하지 않는다. 이번 단계에서 공통 판정·트레이스·교환·복사·
복원·비교를 연결했다. 변신/괴짜/일루전 등 개별 특성 소유의 직접 접근은
페이즈 3 효과 정비에서 해당 효과 단위로 연결한다. 두 슬롯 요약/화면은 페이즈 8에서
세 슬롯 조회 API에 연결한다. 모든 직접 읽기를 무차별적으로 바꾸지는 않는다.

배정표 적용/일반 개별 효과는 페이즈 3, 영구 형태·저장은 페이즈 4,
강화 개별 효과(전지전능Ⅱ 심판 포함)는 페이즈 7이다.
현재 스토리/기존 저장 개체를 새 단계로 자동 변환하지 않는다.

## 검증

`verify.py`, `verify_phase1.py`, `verify_phase2.py`를 실행한다.
페이즈 1은 phase 1 경로를 명시적으로 회귀 검증하며 페이즈 2는 현재 manifest를 사용한다.
기존 영문 풀스택을 메모리에만 읽어 적용하고 GCC로 링크한 ARM 코드를 Unicorn에서 실행한다.
206개 종류의 일반/강화, 세 슬롯 판정, 위액/도구/화학변화가스, 실제 스킬스왑·역할·
트레이스·복원 경로, 중복 및 중첩 행동, 잘못된 프로필, 개체 재사용,
스피드 등급·날씨 발생원 등급/컴포넌트 저장, 명령어/동굴/원본 해시를 검증한다.
UI/애니메이션, 원래 종족값 조회, 난수와 도구 결과는 하네스에서 제공한다.
실제 플레이 화면, 개별 강화 효과 전부, 저장 파일의 자동 연동은 이 테스트 범위가 아니다.

동굴은 적용 시 예약/참조를 확인해 0x4000바이트를 동적으로 할당한다.
team_push 및 overlay36 보호 영역을 사용하지 않는다.
풀스택 재빌드, NDS/세이브 출력, 에뮬레이터 플레이는 수행하지 않는다.
